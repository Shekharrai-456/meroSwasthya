# Security — Swasthya Card

A threat table, not a checklist, per CLAUDE.md §5's Session 1 instruction. Each row names the concrete implementation, not just a library. "Where implemented" gives the actual file/module from `docs/ARCHITECTURE.md`'s directory tree; "How tested" gives the actual test file/case, most of which are already named as requirements in `docs/REQUIREMENTS.md`.

| # | Threat | Where this app is exposed | Control | Where implemented | How tested |
|---|---|---|---|---|---|
| 1 | PIN/credential theft from storage | `users.pin_hash` column; device-side PIN hash | Server: argon2id hashing, no plaintext PIN ever persisted or logged (REQ-SEC-005, REQ-USER-002). Device: PIN hash + DB key material live only in `flutter_secure_storage`, never `SharedPreferences` (REQ-AUTH-017) | `modules/auth/service.ts` (`argon2.hash`/`argon2.verify`); Flutter `core/net` / secure-storage wrapper | `test/auth.test.ts`: DB row for a test user never contains the raw PIN; response bodies from `pin/set`/`pin/login` asserted to never contain `pinHash` |
| 2 | Brute-forcing the PIN | `POST /auth/pin/login` | Two stacked controls (OPEN_QUESTIONS Q6, resolved A): (a) `@fastify/rate-limit` — 10 req/15 min keyed on `ip+phone`; (b) a Redis counter incrementing on each wrong PIN, locking the **account** for 15 min after 5 failures, independent of caller IP (REQ-AUTH-006, REQ-SEC-001) | `plugins/ratelimit.ts` (a); `modules/auth/service.ts` `checkPinLockout()` (b) | `test/auth.test.ts`: 5 wrong PINs from *different* IPs still locks the account (proves (b) isn't just IP-based); 11th request from one IP+phone within 15 min gets 429 regardless of PIN correctness (proves (a)) |
| 3 | Brute-forcing / flooding OTP requests | `POST /auth/otp/request` | Rate limit 5/10min/phone (REQ-AUTH-002); OTP itself is a random 6-digit code in `OTP_MODE=real` (fixed `123456` only in `OTP_MODE=demo`, never in a prod-configured deployment) | `plugins/ratelimit.ts`; `modules/auth/service.ts` | `test/auth.test.ts`: 6th request in 10 min → 429 `RATE_LIMITED` |
| 4 | Token forgery / signature stripping | Every `Authorization: Bearer` header; every QR payload | Access tokens and grant tokens are signed with **two separate** HS256 secrets (`JWT_SECRET`, `GRANT_SECRET`) via `jose`'s `SignJWT`/`jwtVerify`, which reject `alg:"none"` and any algorithm not explicitly allowed (REQ-AUTH-010, REQ-GRANT-001). `typ` claim (`access`/`temp`/`grant`) is checked on every verify, so a valid grant token can never be replayed as an access token or vice versa (REQ-ROLE-008) | `plugins/auth.ts` (`requireAuth`), `modules/grants/service.ts` | `test/auth.test.ts` + `test/grants.test.ts`: a grant token presented as a Bearer access token → 401; an access token presented as a grant `qrPayload` → rejected before JWT verify even runs (wrong prefix) |
| 5 | Refresh-token theft / replay after rotation | `POST /auth/refresh` | Refresh tokens are opaque (not JWTs), stored **hashed** (never the raw token), single-use: a successful refresh revokes the old token and issues a new pair. **Add explicit reuse-detection**: if a refresh token whose row is already `revokedAt != null` is presented again, treat it as a stolen/replayed token and revoke every other active refresh token for that `userId` (standard rotation-reuse defense — not explicitly in backend.md, added here because CLAUDE.md §9's "Auth session" testing rules require it and REQ-AUTH-011 only specifies storage, not reuse handling) | `modules/auth/service.ts` `rotateRefreshToken()` | `test/auth.test.ts`: reuse of an already-rotated refresh token → 401, and a second, previously-valid refresh token for the same user is now also revoked |
| 6 | Vertical privilege escalation (wrong role calling an endpoint) | Every role-gated route | `requireRole(...)` checked in the route handler before the service runs (REQ-ROLE-002); `fchv` additionally hard-blocked from `visits` both at the route (REQ-VISIT-001) and again inside `sync/service.ts`'s per-change authorization (REQ-SYNC-003) — two independent enforcement points for the one role restriction called out three times in the spec | `plugins/auth.ts`, `modules/visits/routes.ts`, `modules/sync/service.ts` | REQ-TEST matrix (CLAUDE.md §10): every protected endpoint × every role, generated from a table, asserting allow/deny |
| 7 | Horizontal / object-level privilege escalation (user A reads/writes user B's patient) | Every `:id`-scoped patient endpoint | `canReadPatient`/`canAppendPatient` re-derived from `(user, patientId)` on every request — ownership or an active, unrevoked, unexpired grant, nothing cached or trusted from the token (REQ-ROLE-003/004) | `plugins/auth.ts` | REQ-TEST matrix: user A's token against user B's `patientId` on every endpoint → 403/404 consistently, never a silent 200 with the wrong data |
| 8 | Grant-token misuse (QR sharing) | `POST /grants/redeem` | Single-purpose token (`typ:"grant"`), expires in 10 min if unredeemed, 24 h access window after redeem, one redemption per grant (second redeemer → 409, not silently allowed) (REQ-GRANT-004..009), revocable at any time by the owner ending provider access **immediately** (REQ-GRANT-008/009) | `modules/grants/service.ts` | `test/grants.test.ts`: full lifecycle incl. expired, already-redeemed, revoked, and the 24 h-after-redeem boundary (A.6 case 16) |
| 9 | SQL / NoSQL injection | Any endpoint accepting user input that reaches the database | Prisma's parameterized query builder for all reads/writes — **no raw SQL string interpolation anywhere**, including the raw-SQL migration additions in `docs/DATA_MODEL.md` (those are static DDL run once at migrate time, never built from request input) | Every `modules/*/service.ts` | Standard Prisma usage makes this largely non-testable-as-a-bug-class; code review checklist item in Session 6 confirms no `$queryRawUnsafe`/string-built SQL exists anywhere in the codebase |
| 10 | CORS misconfiguration | Every browser-originated request (the demo web page, and any future admin web dashboard) | `CORS_ORIGINS=*` is explicitly documented as **hackathon-only** (REQ-SEC-002); `@fastify/cors` reads the origin list from config, not hard-coded, so a production deployment sets a real allowlist without a code change | `plugins/` cors registration in `app.ts`; `config.ts` | Session 6 hardening pass explicitly re-checks this value is not `*` before any non-demo deployment (documented as a required manual gate, since there's no automated test that can distinguish "intentional demo" from "forgotten to lock down") |
| 11 | Rate-limit gaps on cost-bearing endpoints | `POST /documents/presign`, `POST /documents/:id/complete` | **Gap identified in Session 0 (GAP G4), closed here:** add the same `@fastify/rate-limit` plugin to the documents module — 30 presign requests/hour/user (generous enough for normal paper-capture use, tight enough to block scripted abuse of presigned-URL generation or storage-cost exhaustion) | `plugins/ratelimit.ts`, `modules/documents/routes.ts` | `test/documents.test.ts`: 31st presign request in an hour → 429 |
| 12 | Secure headers missing (clickjacking, MIME sniffing, etc.) | Every HTTP response | `@fastify/helmet` registered globally with defaults (REQ-SEC-003) — no custom CSP is added because this API serves no HTML pages of its own except the mock-SMS demo page, which is intentionally simple and has no user-supplied content to inject | `app.ts` plugin registration | Session 6: assert `X-Frame-Options`/`X-Content-Type-Options` present on a sample response |
| 13 | Secrets in source control or logs | `.env`, `JWT_SECRET`, `GRANT_SECRET`, `S3_SECRET_KEY`, `SPARROW_TOKEN`, `ANTHROPIC_API_KEY` | `.env` git-ignored; `.env.example` committed with every key present and a dummy value (CLAUDE.md §7); `config.ts` never logs the parsed config object wholesale (only individual non-secret fields like `smsMode`); pino redaction paths configured for any accidental secret-shaped field name | `config.ts`, `.gitignore`, pino logger setup in `app.ts` | Session 2: grep the repo for the literal example `.env` values to confirm `.gitignore` actually excludes the real file; Session 6: confirm no log line in a full smoke-test run contains a secret pattern |
| 14 | PII/PHI/secrets in application logs | Every request log line | Never logged at any level: PINs, OTPs, JWT/refresh token values, SMS message bodies (REQ-SEC-004). Standard request log is `{method, path, status, ms, userId, requestId}` only — no request/response bodies logged by default | `app.ts` pino request logging | Session 6: run the full smoke script, grep the log output for phone numbers/PINs/token substrings — must be empty except `userId` (a UUID, not the phone itself) |
| 15 | Upload abuse: oversized files, wrong content type, extension/content mismatch | `POST /documents/presign`, the presigned `PUT`, `POST /documents/:id/complete` | Size capped at 2 MB at the presign request boundary (zod); content type restricted to `image/jpeg` only (REQ-DOC-001, OPEN_QUESTIONS Q3); `complete` does a `HEAD` on the actual stored object and — **added control, not explicit in backend.md but required by CLAUDE.md §15's upload rule** — verifies the object's actual `Content-Length` and a magic-byte sniff of the first bytes match a real JPEG before flipping `status → uploaded`, so a client can't presign as `image/jpeg` and then `PUT` an arbitrary file type past the content-type header alone | `modules/documents/service.ts`, `modules/documents/storage.ts` | `test/documents.test.ts`: oversized file rejected at presign; a non-JPEG byte stream `PUT` to a `image/jpeg`-presigned URL is rejected at `complete` (magic-byte check fails) rather than silently marked `uploaded` |
| 16 | Path traversal via object key | Storage layer | Object key is entirely server-generated (`patients/{patientId}/{documentId}.jpg`, both ids are UUIDs already validated as UUIDs by zod) — the client never supplies any part of the storage path, so there is no traversal surface to exploit (REQ-DOC-002, REQ-DOC-008) | `modules/documents/storage.ts` | `test/documents.test.ts`: presign response's `objectKey` is asserted to match the fixed template regardless of what `title`/`type` the client sent |

| 20 | Payment handling | *Not applicable — no payment flow exists in any feature tier of this product.* | — | — | — |
| 21 | Sync-endpoint authorization bypass via batched requests | `POST /sync/push` | Each change in the batch is authorized **independently**, per its own `table`/`rowId`/acting user — REQ-SYNC-003's per-table rule (`visits` excludes `fchv`, etc.) is evaluated inside the push loop itself, not once for the whole request, so a batch can't smuggle an unauthorized write for one patient inside an otherwise-authorized batch for another | `modules/sync/service.ts` | `test/sync.test.ts`: a batch mixing an authorized change and one the caller shouldn't be allowed to make → the authorized one applies, the unauthorized one is individually `rejected FORBIDDEN`, not the whole batch |

## Notes on scope

Rows 19 and 20 (webhooks, payments) are marked not-applicable rather than omitted, per CLAUDE.md §5's instruction to cover the full threat checklist explicitly — this product genuinely has neither surface, and inventing controls for a non-existent attack surface would be exactly the over-engineering CLAUDE.md §15 warns against.

Two controls above (rows 5 and 11, and part of row 15) are **added beyond what `documentation/backend.md` explicitly specifies**, because CLAUDE.md's own security/testing rules (§9, §10, §15) require them regardless of whether the product spec called them out by name. These are flagged inline rather than silently introduced, so a reviewer can see exactly where this document goes beyond the frozen product spec and why.
