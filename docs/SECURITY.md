# Security — Swasthya Card

A threat table, not a checklist, per CLAUDE.md §5's Session 1 instruction. Each row names the concrete implementation, not just a library. "Where implemented" gives the actual file/module from `docs/ARCHITECTURE.md`'s directory tree; "How tested" gives the actual test file/case, most of which are already named as requirements in `docs/REQUIREMENTS.md`.

| # | Threat | Where this app is exposed | Control | Where implemented | How tested |
|---|---|---|---|---|---|
| 1 | PIN/credential theft from storage | `users.pin_hash` column; device-side PIN hash | Server: argon2id hashing, no plaintext PIN ever persisted or logged (REQ-SEC-005, REQ-USER-002). Device: PIN hash + DB key material live only in `flutter_secure_storage`, never `SharedPreferences` (REQ-AUTH-017) | `modules/auth/service.ts` (`argon2.hash`/`argon2.verify`); Flutter `core/net` / secure-storage wrapper | `test/auth.test.ts`: DB row for a test user never contains the raw PIN; response bodies from `pin/set`/`pin/login` asserted to never contain `pinHash` |
| 2 | Brute-forcing the PIN | `POST /auth/pin/login` | Two stacked controls (OPEN_QUESTIONS Q6, resolved A): (a) a custom Redis fixed-window counter — 10 req/15 min keyed on `ip+phone` (**not** `@fastify/rate-limit`, corrected in Session 3: that plugin's key generator runs before the body is parsed, so it can't key on a phone number - see OPEN_QUESTIONS Q6's implementation-correction note); (b) a separate Redis counter incrementing on each wrong PIN, locking the **account** for 15 min after 5 failures, independent of caller IP (REQ-AUTH-006, REQ-SEC-001). **Session 8 addition:** a nonexistent phone or a user with no `pinHash` used to short-circuit before ever running argon2, responding far faster than a real wrong-PIN attempt - a timing side-channel around the same "unregistered vs. registered" distinction this row's identical-error-message design already tried to hide. `loginWithPin` now always runs a real `verifyPin` (against the real hash, or `DUMMY_PIN_HASH` when there is none) before responding either way | `lib/rateLimiter.ts` (both (a) `checkFixedWindowLimit` and (b) `checkPinLockout`/`recordPinFailure`); `lib/hash.ts` (`DUMMY_PIN_HASH`); called from `modules/auth/service.ts` `loginWithPin()` | `test/auth.test.ts`: 5 wrong PINs locks the account (proves (b)); 11th all-correct request from one IP+phone within 15 min gets 429 regardless (proves (a) is a separate, independently-tripping counter); a new timing-comparison test proves an unregistered phone now takes comparable time to a wrong-PIN attempt on a real account |
| 3 | Brute-forcing / flooding OTP requests | `POST /auth/otp/request` | Rate limit 5/10min/phone (REQ-AUTH-002); OTP itself is a random 6-digit code in `OTP_MODE=real` (fixed `123456` only in `OTP_MODE=demo`, never in a prod-configured deployment) | `plugins/ratelimit.ts`; `modules/auth/service.ts` | `test/auth.test.ts`: 6th request in 10 min → 429 `RATE_LIMITED` |
| 4 | Token forgery / signature stripping | Every `Authorization: Bearer` header; every QR payload | Access tokens and grant tokens are signed with **two separate** HS256 secrets (`JWT_SECRET`, `GRANT_SECRET`) via `jose`'s `SignJWT`/`jwtVerify`, which reject `alg:"none"` and any algorithm not explicitly allowed (REQ-AUTH-010, REQ-GRANT-001). `typ` claim (`access`/`temp`/`grant`) is checked on every verify, so a valid grant token can never be replayed as an access token or vice versa (REQ-ROLE-008). **Session 6 hardening addition:** the two secrets being equal (which would collapse this design to one shared secret) is now rejected at process startup via a zod `.refine()`, not just documented as a `.env.example` convention | `plugins/auth.ts` (`requireAuth`), `modules/grants/service.ts`, `config.ts` (startup `.refine()`) | `test/auth.test.ts` + `test/grants.test.ts`: a grant token presented as a Bearer access token → 401; an access token presented as a grant `qrPayload` → rejected before JWT verify even runs (wrong prefix); `test/foundation.test.ts`: equal `JWT_SECRET`/`GRANT_SECRET` fails config parsing at startup |
| 5 | Refresh-token theft / replay after rotation | `POST /auth/refresh` | Refresh tokens are opaque (not JWTs), stored **hashed** (never the raw token), single-use: a successful refresh revokes the old token and issues a new pair. **Add explicit reuse-detection**: if a refresh token whose row is already `revokedAt != null` is presented again, treat it as a stolen/replayed token and revoke every other active refresh token for that `userId` (standard rotation-reuse defense — not explicitly in backend.md, added here because CLAUDE.md §9's "Auth session" testing rules require it and REQ-AUTH-011 only specifies storage, not reuse handling) | `modules/auth/service.ts` `rotateRefreshToken()` | `test/auth.test.ts`: reuse of an already-rotated refresh token → 401, and a second, previously-valid refresh token for the same user is now also revoked |
| 6 | Vertical privilege escalation (wrong role calling an endpoint) | Every role-gated route | `requireRole(...)` checked in the route handler before the service runs (REQ-ROLE-002); `fchv` additionally hard-blocked from `visits` both at the route (REQ-VISIT-001) and again inside `sync/service.ts`'s per-change authorization (REQ-SYNC-003) — two independent enforcement points for the one role restriction called out three times in the spec | `plugins/auth.ts`, `modules/visits/routes.ts`, `modules/sync/service.ts` | REQ-TEST matrix (CLAUDE.md §10): every protected endpoint × every role, generated from a table, asserting allow/deny |
| 7 | Horizontal / object-level privilege escalation (user A reads/writes user B's patient) | Every `:id`-scoped patient endpoint | `canReadPatient`/`canAppendPatient` re-derived from `(user, patientId)` on every request — ownership or an active, unrevoked, unexpired grant, nothing cached or trusted from the token (REQ-ROLE-003/004) | `plugins/auth.ts` | REQ-TEST matrix: user A's token against user B's `patientId` on every endpoint → 403/404 consistently, never a silent 200 with the wrong data |
| 8 | Grant-token misuse (QR sharing) | `POST /grants/redeem` | Single-purpose token (`typ:"grant"`), expires in 10 min if unredeemed, 24 h access window after redeem, one redemption per grant (second redeemer → 409, not silently allowed) (REQ-GRANT-004..009), revocable at any time by the owner ending provider access **immediately** (REQ-GRANT-008/009). **Session 8 addition:** `ttlMinutes` on `POST /grants` had no upper bound, letting a caller mint a Tier-1 grant valid for months/years - functionally the Tier-2 "printed long-lived QR" feature (REQ-GRANT-012) without that feature's required PIN-at-redeem safeguard. Capped at 60 minutes | `modules/grants/service.ts`, `modules/grants/schemas.ts` (`GRANT_TTL_MINUTES_MAX`) | `test/grants.test.ts`: full lifecycle incl. expired, already-redeemed, revoked, and the 24 h-after-redeem boundary (A.6 case 16); `ttlMinutes` above/at the 60-minute cap rejected/accepted |
| 9 | SQL / NoSQL injection | Any endpoint accepting user input that reaches the database | Prisma's parameterized query builder for all reads/writes — **no raw SQL string interpolation anywhere**, including the raw-SQL migration additions in `docs/DATA_MODEL.md` (those are static DDL run once at migrate time, never built from request input) | Every `modules/*/service.ts` | Standard Prisma usage makes this largely non-testable-as-a-bug-class; code review checklist item in Session 6 confirms no `$queryRawUnsafe`/string-built SQL exists anywhere in the codebase |
| 10 | CORS misconfiguration | Every browser-originated request (the demo web page, and any future admin web dashboard) | `CORS_ORIGINS=*` is explicitly documented as **hackathon-only** (REQ-SEC-002); `@fastify/cors` reads the origin list from config, not hard-coded, so a production deployment sets a real allowlist without a code change. **Phase 10 hardening (Session 16), closed the manual-gate half of this:** `config.ts`'s own `.refine()` now refuses to boot at all with `NODE_ENV=production` and `CORS_ORIGINS=*` still set, rather than relying only on a documented manual pre-deployment check | `plugins/` cors registration in `app.ts`; `config.ts` | `test/foundation.test.ts`: `NODE_ENV=production` + `CORS_ORIGINS=*` → config parse fails; a restricted origin list under the same `NODE_ENV` → succeeds; the wildcard is still accepted outside production |
| 11 | Rate-limit gaps on cost-bearing endpoints | `POST /documents/presign`, `POST /documents/:id/complete` | **Gap identified in Session 0 (GAP G4), closed in Phase 10 hardening (Session 16):** both routes now call the same Redis-backed fixed-window limiter every other business-rule rate limit in this codebase uses (`lib/rateLimiter.ts`'s `checkFixedWindowLimit`, REQ-SEC-001) - 30 requests/hour/actor for each, independently | `modules/documents/service.ts` (`assertUnderRateLimit`) | `test/documents.test.ts`: 31st presign in an hour for the same user → 429; 31st complete call → 429 |
| 12 | Secure headers missing (clickjacking, MIME sniffing, etc.) | Every HTTP response | `@fastify/helmet` registered globally with defaults (REQ-SEC-003) — no custom CSP is added because this API serves no HTML pages of its own except the mock-SMS demo page, which is intentionally simple and has no user-supplied content to inject | `app.ts` plugin registration | Session 6: assert `X-Frame-Options`/`X-Content-Type-Options` present on a sample response |
| 13 | Secrets in source control or logs | `.env`, `JWT_SECRET`, `GRANT_SECRET`, `S3_SECRET_KEY`, `SPARROW_TOKEN`, `ANTHROPIC_API_KEY` | `.env` git-ignored; `.env.example` committed with every key present and a dummy value (CLAUDE.md §7); `config.ts` never logs the parsed config object wholesale (only individual non-secret fields like `smsMode`); pino redaction paths configured for any accidental secret-shaped field name | `config.ts`, `.gitignore`, pino logger setup in `app.ts` | Session 2: grep the repo for the literal example `.env` values to confirm `.gitignore` actually excludes the real file; Session 6: confirm no log line in a full smoke-test run contains a secret pattern |

| 15 | Upload abuse: oversized files, wrong content type, extension/content mismatch | `POST /documents/presign`, the presigned `PUT`, `POST /documents/:id/complete` | Size capped at 2 MB at the presign request boundary (zod); content type restricted to `image/jpeg` only (REQ-DOC-001, OPEN_QUESTIONS Q3). **Phase 10 hardening (Session 16), closed:** `complete` now also verifies the real uploaded object's `Content-Length` against the `sizeBytes` declared at presign time (persisted as `Document.declaredSizeBytes`) and against the absolute 2 MB cap independently, and downloads the object to check its first 3 bytes are a real JPEG SOI signature (`0xFF 0xD8 0xFF`) before ever flipping `status → uploaded` | `modules/documents/service.ts` (`completeDocument`, `looksLikeJpeg`) | `test/documents.test.ts`: an uploaded object whose real bytes aren't a JPEG → rejected; an object larger than its declared `sizeBytes` → rejected; a real JPEG-signed buffer within the declared size → accepted |

| 21 | Sync-endpoint authorization bypass via batched requests | `POST /sync/push` | Each change in the batch is authorized **independently**, per its own `table`/`rowId`/acting user — REQ-SYNC-003's per-table rule (`visits` excludes `fchv`, etc.) is evaluated inside the push loop itself, not once for the whole request, so a batch can't smuggle an unauthorized write for one patient inside an otherwise-authorized batch for another | `modules/sync/service.ts` | `test/sync.test.ts`: a batch mixing an authorized change and one the caller shouldn't be allowed to make → the authorized one applies, the unauthorized one is individually `rejected FORBIDDEN`, not the whole batch |

## Notes on scope

Rows 19 and 20 (webhooks, payments) are marked not-applicable rather than omitted, per CLAUDE.md §5's instruction to cover the full threat checklist explicitly — this product genuinely has neither surface, and inventing controls for a non-existent attack surface would be exactly the over-engineering CLAUDE.md §15 warns against.

Two controls above (rows 5 and 11/15) are **added beyond what `documentation/backend.md` explicitly specifies**, because CLAUDE.md's own security/testing rules (§9, §10, §15) require them regardless of whether the product spec called them out by name — flagged inline so a reviewer can see exactly where this document goes beyond the frozen product spec and why. Rows 11 and 15 were open follow-ups tracked in `docs/PROJECT_PLAN.md` Phase 10 through Session 15; both were closed in Session 16's hardening pass (Documents-route rate limiting; upload magic-byte + size verification).
